## September 23 — Paste Stack (working; look provisional)

Paste Stack had been deferred since September 15 ("return to the saved Stack design later"). With the instruction to continue to full parity, it is now built from the saved design and Paste's help ("Using Paste Stack").

- **Shortcut:** ⇧⌘C (Settings › Shortcuts › Activate Paste Stack, as in Paste's first shortcut group) opens and closes a small floating Stack window. Global shortcuts now answer only to their own hot key ID, so several can be registered at once.
- **Collecting:** while the window is open, every accepted copy joins the Stack in copy order. Repeated copies are separate entries, independent of history's duplicate merging.
- **Pasting:** while the Stack is open, holds entries and Accessibility is granted, ⌘V is taken system-wide. It writes the next entry to the clipboard, sends ⌘V to the frontmost app with the Stack's own ⌘V released, and removes the entry. A failed clipboard write keeps the entry. Otherwise ⌘V stays with the system.
- **Controls:** an arrows button reverses the order (Paste: "change the direction of the stack by clicking on the arrows button"), and the context menu's Delete removes an entry. The window grows with its entries up to the 438-pt height of Paste's storyboard, and its frame is saved.
- **Checks:** `PasteStack` core check (order, duplicates, reverse, consume, delete); `--demo --check-stack` (collects only while open, order, reverse, delete, close).
- **Not verified:** a real ⌘V into another app through the Stack. **Unknown until Paste's Stack is observed:** its window layout and styling, where it opens, what it shows when empty, and whether entries survive closing it. Paste's storyboard (264 pt wide, a list, a scroller, a title and two small buttons) and its saved frame (264×76 when empty) are the only evidence so far. The two-finger swipe to delete described in the help is iOS.

## September 23 — long histories: no item cap, lazy content, fast search

Paste limits history by age only (Keep History: Day, Week, Month, Year, Forever; its strings table warns "Unlimited history may increase your disk space usage"). Elmers had also capped history at 2,000 unpinned items, because every payload was held in memory.

- **Lazy content.** Representations over 64 KB (`HistoryStore.inlineLimit`), other than text types, stay in the database when history loads. `ClipboardPayload.items` reads them on use through a separate read-only connection (`RepresentationReader`). Each read checks the item's fingerprint, so bytes another process has since replaced are never mixed into an older item. Card thumbnails read and decode off the main thread, and cards check for an image by type instead of reading it.
- **No partial writes.** Saving reads deferred content with `materializedItems()`, which throws. If content can no longer be read because another writer deleted or replaced the item, that writer's change stands and the item is left out of the save; a partial payload is never written. Deleting and editing keep the old bytes for undo (`retainDeferred()`). Duplicate merging, copy, paste and drag refuse a partial payload.
- **No item cap.** Retention now prunes by age alone (`limit: .max`).
- **Search.** Every item keeps a folded search key (case and diacritics) that updates when its text, source, title, recognized text or link title changes, and search is a byte comparison. Over 20,000 items a search took 279 ms before and 2.9 ms after.
- **Measured** (`ElmersCoreChecks --storage-benchmark`, release build): 20,000 items, one in ten a 250 KB image (500 MB of images). Load 280 ms, adding 24.7 MB of resident memory. One deferred image read 0.5 ms. Save of the whole history 2.4 s (only on first write).
- **Live store** (read-only report): 7 items, 1 with deferred content, which read back intact against its fingerprint.
- **Checks:** core 65/65. Six new checks cover on-demand reading, a rename not touching stored bytes, undo of a deletion restoring retained bytes, an unreadable item never saved partially, an edited item never reading its replacement, and a duplicate merge keeping a lazy image's bytes.
- **Not yet measured:** scrolling and filtering in the panel with a 20,000-item history (the interaction and scroll checks need an idle Mac); search results are not ranked.

## September 21 — SQLite history storage

- **Incremental storage — implemented.** `HistoryStore` stores item metadata, representations, pins and ordered pinboards in the system SQLite library. A save compares against the last loaded state and writes only changed rows in one transaction. The schema is versioned, newer or damaged databases are rejected without replacement, and the database, WAL and shared-memory files are mode 0600 inside the mode-0700 Elmers directory.
- **Verified conversion and recovery.** First conversion builds a staging database, reloads it, compares every item and pinboard, then retains the original under a unique `history.plist.migrated[-N]` name. Real validation found an already-converted four-item database alongside a two-item plist written later by an older build. Recovery conservatively unions both histories inside an immediate transaction on the existing database, leaving live database/WAL/SHM files in place. Before writing, it retains the raw plist and builds an exactly verified pre-merge SQLite snapshot in a private recovery directory; afterward it archives the later plist as `history.plist.recovered[-N]`. The real result was 6 items and 2 pinboards; no item existed under the same UUID in both stores. The prior one-item migrated plist and pre-SQLite backup remained unchanged. Rollback exports use fresh unique `history.plist.post-sqlite[-N]` names so an older export is never overwritten or mistaken for current history.
- **Evidence.** Before recovery: `history.plist` = 2 items / 0 pinboards / identity `3a4c13723b81`; `history.sqlite` = 4 items / 2 pinboards / identity `5377c32da733`; existing migrated plist = 1 item / 2 pinboards / identity `5314461d5c5e`. After recovery: SQLite = 6 items / 2 pinboards / identity `d95d7778ed63`. The synthetic live-capture check passed and produced a 7-item identity `da39adb1fbc1`; quitting and relaunching retained that exact count and identity, with no `history.plist` reappearing. The original real recovery directory is mode 0700 and contains mode-0600 raw copies captured before the transaction hardening; current recovery leaves the active SQLite triplet untouched and stores a verified logical database snapshot plus the raw plist. Active files and retained archives are mode 0600.
- **Benchmark.** A synthetic 2,000-item / roughly 57 MB history measured: plist full save 214.7 ms, plist load 54.7 ms, first SQLite conversion 359.1 ms, one rename 15.9 ms, one new 5 MB image 49.3 ms, one deletion 13.1 ms, SQLite load 57.0 ms. Conversion is one-time; ordinary metadata changes no longer rewrite every payload.
- **Verification.** `scripts/test.sh` passes 45 checks with zero failures (39 at the original checkpoint, plus out-of-order plist conversion, tied-timestamp recovery, backup reuse across a repeated failing recovery, a rename after another writer deleted the row, and a save that fails mid-transaction), including incremental writes, exact conversion, divergent-store recovery with another writer still open, single-snapshot reads during 200 concurrent saves, unique retirement beside an existing migrated archive, corrupt reappeared-plist protection, private backups and fresh non-overwriting rollback exports. The rebuilt app passed all synthetic interaction, status-item, screenshot, sound and image-scroll suites; the latter measured 183 steps, p95 9.45 ms, max 15.79 ms, with no frame over 16.7 ms. A fixture-only real-store check used `AppModel` to create two uniquely identified synthetic items and a temporary pinboard, pin and rename one item, delete the other, reload from disk to verify all four mutations, then remove the fixtures and reload again to verify cleanup. The real store returned to its unchanged 7-item / 2-pinboard identity `da39adb1fbc1`. The product change still emits the pre-existing non-Sendable closure warning in the interaction harness build.
- **Multi-writer safety and order tolerance (review fixes, September 22).** Conversion canonicalises the legacy history (stable sort, newest first) before building the staging database, and verification matches items by id with the stored order checked separately as `copiedAt`-descending, so a plist written by a build that inserted captures at the front, or a merge where a pre-existing row and a new row share a timestamp, converts instead of failing on every launch. A recovery that keeps failing no longer adds a full-size `history-recovery-<UUID>` directory per launch: the backup is taken before the merge transaction and reused when it already holds those exact plist bytes. Each save reads `PRAGMA data_version` first and rebuilds its item baseline from the database when another connection has committed, so an item another process deleted and this one then renames is written back with its representations; rows this writer never stored are still never deleted. `history.sqlite` is created at mode 0600 before SQLite opens it, so its journal, WAL and shared-memory files inherit that mode from the start.
